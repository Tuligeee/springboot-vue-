# 高考志愿填报系统程序文档（毕业答辩版）

## 1. 项目概述

### 1.1 项目名称
基于 Spring Boot + Vue 的高考志愿填报辅助系统

### 1.2 项目定位
本系统面向高考志愿填报场景，围绕“院校查询、专业查询、分数线查询、学生档案管理、模拟志愿填报、资讯公告、交流论坛、后台管理”构建一个前后端分离的信息化平台。系统既服务于普通考生，也支持学校管理员和系统管理员分别从不同视角使用系统。

### 1.3 项目目标
1. 为考生提供便捷的院校、专业与历年分数线查询能力。
2. 为考生提供学生档案维护和多方案模拟填报能力。
3. 在志愿填报时结合学生选考科目，对专业要求进行自动匹配校验。
4. 为学校管理员提供本校招生信息、专业信息和填报热度管理能力。
5. 为系统管理员提供用户、角色、菜单、字典、公告、统计看板等后台管理能力。

### 1.4 项目特点
1. 采用前后端分离架构，前端和后端职责清晰。
2. 基于 JWT 的无状态登录认证，便于接口保护与角色控制。
3. 基于角色的动态路由和权限菜单，实现多角色差异化界面。
4. 支持 Excel 批量导入院校及专业数据，并提供异步导入进度反馈。
5. 志愿填报支持 5 份方案保存，适合考生多方案比较。
6. 在填报阶段自动校验选科要求，降低无效志愿风险。

## 2. 技术架构

### 2.1 总体架构
本项目采用典型的 B/S 架构和前后端分离模式：

1. 前端负责页面展示、交互逻辑、状态管理与接口调用。
2. 后端负责业务处理、权限校验、数据库访问、文件导入导出与统计分析。
3. MySQL 负责业务数据和系统管理数据持久化存储。

系统整体流程如下：

1. 用户通过浏览器访问 Vue 前端页面。
2. 前端调用 Spring Boot 提供的 RESTful 接口。
3. 后端经 Spring Security 校验身份与权限。
4. 业务层调用 MyBatis-Plus Mapper/Repository 访问 MySQL。
5. 后端将统一格式的 JSON 数据返回给前端展示。

### 2.2 前端技术栈
根据 `前端代码/example-ui/package.json` 扫描，前端主要技术如下：

1. `Vue 2.6.12`：构建单页应用。
2. `Vue Router 3.4.9`：实现路由跳转和权限路由。
3. `Vuex 3.6.0`：统一管理用户、权限、标签页等状态。
4. `Element UI 2.15.5`：构建后台及门户页面组件。
5. `Axios 0.21.0`：发送 HTTP 请求。
6. `ECharts 4.9.0`：实现管理员统计看板。
7. `Quill`：富文本编辑。
8. `vue-cropper`：头像裁剪等图片处理。

### 2.3 后端技术栈
根据 `后端代码/example/pom.xml` 与 `后端代码/example/deploy/pom.xml` 扫描，后端主要技术如下：

1. `Spring Boot 2.2.13.RELEASE`：快速搭建后端应用。
2. `Spring MVC`：提供 REST 接口。
3. `Spring Security`：认证与授权。
4. `JWT`：生成与解析登录令牌。
5. `MyBatis-Plus 3.4.0`：简化 ORM 开发。
6. `PageHelper`：分页查询。
7. `Druid`：数据库连接池。
8. `Swagger 3`：接口文档。
9. `Lombok`：简化 Java 实体和构造代码。
10. `Apache POI`：Excel 导入导出。
11. `Caffeine`：本地缓存。
12. `OSHI + JNA`：服务器监控信息采集。

## 5. 前端系统设计

### 5.1 前端入口与路由机制
前端路由文件位于 `前端代码/example-ui/src/router/index.js`。系统路由分为常量路由和动态路由两类：

1. 常量路由用于登录、注册、错误页、门户首页等基础页面。
2. 动态路由由后端返回菜单数据生成，体现不同角色的可访问模块。

从路由设计看，系统将页面分为三种布局：

1. `Layout`
传统后台管理布局，适合管理员使用。

2. `PortalLayout`
门户型布局，适合普通考生浏览院校、资讯、论坛等公共业务页面。

3. `DynamicLayout`
根据角色自动切换布局，提升同一套路由在多角色场景下的复用度。

### 5.2 首页设计
首页文件为 `src/views/index.vue`，根据角色显示不同内容：

1. 系统管理员进入 `AdminDashboard`。
2. 学校管理员进入 `SchoolDashboard`。
3. 普通用户进入门户首页。

普通用户首页包含：

1. Banner 轮播图。
2. 系统公告滚动条。
3. 四大功能入口卡片：
院校分数查询、个人档案管理、政策资讯中心、志愿方案管理。
4. 咨询通道展示。

这种设计使首页既具备宣传展示作用，又是核心业务的统一入口。

### 5.3 注册与登录页面
前端提供单独的注册页 `src/views/register.vue` 和登录页 `src/views/login.vue`。注册页对用户名、密码、确认密码做了前端校验，交互流程较完整，适合公众用户注册。

### 5.4 在线志愿填报页面
文件为 `src/views/entrance/aspiration/apply.vue`，是本系统最核心的业务页面之一，功能如下：

1. 支持选择第 1 到第 5 份志愿单。
2. 支持动态添加目标院校。
3. 每个院校下可动态添加多个专业志愿。
4. 前端校验院校是否重复。
5. 前端校验同一院校下专业是否重复。
6. 进入页面时先检查学生档案是否完善。
7. 对不满足选科要求的专业，用明显标记提示“选科不符”。

该页面体现了较强的业务约束能力，而非单纯表单录入。

### 5.5 前端接口调用封装
前端统一通过 `src/utils/request.js` 封装 Axios 请求，具备以下能力：

1. 自动拼接基础路径。
2. 自动添加 `Authorization: Bearer token`。
3. 对 GET 参数统一处理。
4. 对 `401`、`500` 等状态做统一拦截。
5. 登录失效时自动引导重新登录。

这种封装提高了代码复用性，减少了页面重复逻辑。

## 6. 后端系统设计

### 6.1 启动类
后端启动类为 `后端代码/example/deploy/src/main/java/com/mock/example/WebApplication.java`，使用 `@SpringBootApplication` 和 `@EnableAsync` 注解：

1. `@SpringBootApplication` 负责 Spring Boot 自动装配。
2. `@EnableAsync` 表明系统支持异步任务，主要用于 Excel 导入等耗时业务。

### 6.2 分层结构
后端整体采用较清晰的分层设计：

1. `interfaces/controller`
控制层，对外提供 REST API。

2. `interfaces/body`
请求参数对象，承担前端入参封装作用。

3. `interfaces/vo`
返回视图对象，便于后端按需输出字段。

4. `modules/service`
业务逻辑层，处理核心业务规则。

5. `modules/repository` 与 `mapper`
数据访问层，负责数据库持久化。

6. `modules/entity/model`
实体层，映射数据表结构。

7. `common`
公共层，包含配置、异常、分页、缓存、工具类、响应封装等。

### 6.3 统一返回结构
系统大量接口使用 `Response` 和 `TableDataInfo` 作为统一响应结构：

1. `Response` 用于普通对象返回，包含状态码、消息、数据。
2. `TableDataInfo` 用于分页列表返回，包含总数和列表数据。

这有利于前后端约定统一，简化页面处理逻辑。

## 7. 安全认证与权限控制

### 7.1 认证机制
根据 `SecurityConfig.java` 扫描，系统使用 Spring Security + JWT 实现无状态认证。

登录流程如下：

1. 用户向 `/login` 提交用户名和密码。
2. 后端校验账号密码。
3. 校验成功后生成 JWT 令牌。
4. 前端保存令牌。
5. 后续请求在请求头中携带 `Bearer Token`。
6. 后端通过 `JwtAuthenticationTokenFilter` 解析 Token 并识别当前用户。

### 7.2 放行资源
系统对以下资源允许匿名访问：

1. `/login`
2. `/register`
3. `/captchaImage`
4. 静态资源
5. `/public/**`
6. Swagger 文档相关路径
7. Druid 监控相关路径

其他接口默认都需要认证后访问。

### 7.3 权限控制方式
系统在控制器层广泛使用 `@PreAuthorize`：

1. 基于权限字符串控制，如 `@ss.hasPermi(...)`
2. 基于角色控制，如 `@ss.hasAnyRoles('admin')`

说明系统实现了角色权限分离，适合后台管理系统场景。

### 7.4 动态菜单与动态路由
登录后前端会调用：

1. `getInfo`
2. `getRouters`

后端根据当前用户角色返回对应的权限集合和路由菜单，从而实现：

1. 同一套前端代码适配多角色。
2. 未授权菜单不显示。
3. 未授权接口不可访问。

## 8. 核心业务模块分析

### 8.1 用户与系统管理模块
系统保留了成熟的后台管理能力，包括：

1. 用户管理
2. 角色管理
3. 菜单管理
4. 岗位管理
5. 部门管理
6. 字典管理
7. 通知公告
8. 系统配置
9. 在线用户、日志、服务器监控等

这一部分主要继承自 RuoYi-Vue 管理体系，并与本项目业务模块融合。

### 8.2 学生档案模块
控制器为 `CeStudentController`，对应路径 `/college_entrance/student`。

主要功能：

1. 学生列表查询。
2. 学生信息新增、修改、删除。
3. 查询当前登录用户自己的学生档案。
4. 更新当前登录用户自己的学生档案。

核心字段根据 `CeStudent.java` 可总结为：

1. `userId`：绑定系统用户。
2. `studentNo`：学生编号。
3. `studentName`：姓名。
4. `enrollmentYear`：入学年份。
5. `graduateYear`：毕业年份。
6. `sex`：性别。
7. `achievement`：高考成绩。
8. `subjectFirst`：首选科目。
9. `subjectSecond`：再选科目。

该模块是志愿推荐与选科校验的数据基础。

### 8.3 院校管理模块
控制器为 `CeCollegeController`，对应路径 `/college_entrance/college`。

主要功能：

1. 院校列表查询。
2. 院校详情查看。
3. 新增、编辑、删除院校。
4. 查询当前学校管理员所属院校。
5. 导出院校及专业数据。
6. 下载导入模板。
7. 异步导入 Excel 数据。
8. 查询导入进度。
9. 查询唯一办学层次列表。

根据 `CeCollegeService.java`，该模块有几个明显亮点：

1. 学校管理员只能查看或修改自己负责院校的数据。
2. Excel 导入采用异步执行，避免大文件阻塞请求线程。
3. 导入前会将院校和专业数据预加载到内存中进行缓存匹配。
4. 支持“导入时更新已有数据”。
5. 支持进度条和错误日志反馈。

### 8.4 专业管理模块
控制器为 `CeProfessionController`，对应路径 `/college_entrance/profession`。

核心功能：

1. 专业列表分页查询。
2. 专业新增、编辑、删除。
3. 专业详情查看。
4. 按院校维度关联专业。

根据 `CeProfession.java`，专业的核心字段包括：

1. `professionNo`：专业编号。
2. `professionName`：专业名称。
3. `collegeNo`：所属院校编号。
4. `studyYear`：学制。
5. `personCount`：招生人数。
6. `subjectRequirement`：选科要求。
7. `detailInfo`：专业说明。

此外，实体中还封装了分数线文本生成逻辑，便于前端直接展示专业历年录取信息。

### 8.5 分数线模块
系统包含两类分数线能力：

1. `scoreLine`
院校或专业维度的历史分数线。

2. `provinceScore` 与 `provinceLine`
省份维度的历史成绩/省控线信息。

这些模块为考生进行志愿决策提供数据支撑，是系统决策辅助价值的重要来源。

### 8.6 志愿填报模块
控制器为 `CeAspirationController`，对应路径 `/college_entrance/aspiration`。

主要功能：

1. 保存志愿填报方案。
2. 获取 5 份志愿单的状态列表。
3. 获取填报选择项。
4. 删除指定志愿单。
5. 分页查看学生志愿列表。
6. 查看某个学生志愿摘要。
7. 导出志愿单为 Excel。

这是系统的最核心业务模块，其关键设计如下：

1. 每个用户支持 5 份独立志愿单。
2. 系统用 `userId_sheetNo` 作为一个逻辑上的方案标识。
3. 保存志愿单时，会先删除旧方案再保存新方案，保证同一方案号数据唯一。
4. 保存前调用选科校验逻辑，若专业要求与考生选科不匹配，则直接报错。
5. 对院校和专业信息进行结构化保存，便于后续查询、导出、统计。

### 8.7 选科匹配逻辑
在 `CeAspirationService.java` 中，系统实现了比较有代表性的业务校验逻辑：

1. 从学生档案读取首选科目和再选科目。
2. 将学生选科做归一化处理，如去空格、统一科目名称。
3. 将专业的选科要求也做归一化处理。
4. 在提交志愿时逐一判断专业要求是否被学生满足。
5. 不满足时抛出带有院校名、专业名、要求内容的详细错误信息。

这一逻辑体现了系统并非只做信息展示，而是具备一定的规则判断能力。

### 8.8 收藏模块
控制器为 `CeCollectionController`，路径 `/college_entrance/collection`。

主要功能：

1. 收藏列表查询。
2. 新增收藏。
3. 删除收藏。
4. 检查是否已收藏。
5. 一键切换收藏状态。

该模块增强了用户个性化使用体验。

### 8.9 资讯与公告模块
资讯模块控制器为 `CeNewsController`，路径 `/entrance/news`。

1. 资讯列表查询。

3. 点赞资讯。
4. 新增、编辑、删除资讯。

公告模块则复用系统通知公告管理能力。首页会把公告滚动展示给普通用户，增强信息触达效果。

### 8.10 论坛交流模块
控制器为 `CeForumController`，路径 `/entrance/forum`。

主要功能：

1. 帖子列表。
2. 帖子详情。
3. 发布帖子。
4. 编辑帖子。
5. 查看评论。
6. 发布评论。

论坛模块的作用是增强系统互动性，使平台不只是信息查询工具，也具备经验交流能力。

### 8.12 统计分析模块
控制器为 `CeStatisticsController`，路径 `/entrance/statistics`。

接口包括：

1. `/overview`
获取顶部概览统计。

2. `/chart`
获取图表统计数据。

根据 `CeStatisticsServiceImpl.java`，系统对两类角色使用不同统计口径：

1. 系统管理员看全站数据：
用户数、院校数、专业数、志愿数等。

2. 学校管理员看本校相关数据：

这部分增强了系统的数据可视化能力。

## 10. 核心业务流程

### 10.1 用户登录流程
1. 用户输入用户名和密码。
2. 前端调用 `/login` 接口。
3. 后端验证账号密码。
4. 后端签发 JWT。
5. 前端存储 Token，并调用 `getInfo` 和 `getRouters`。
6. 系统根据角色加载对应菜单与页面。

### 10.2 学生档案维护流程
1. 考生登录系统。
2. 进入个人档案页面。
3. 填写成绩、选科、姓名等信息。
4. 前端调用 `myProfile` 相关接口保存。
5. 后端将学生数据与当前用户绑定。

### 10.3 志愿填报流程
1. 考生进入模拟填报页面。
2. 系统自动读取当前志愿单号的数据。
3. 系统先检查学生档案是否完善。
4. 考生添加目标院校。
5. 考生在目标院校下选择多个专业。
6. 前端先做重复校验。
7. 后端再进行选科匹配校验。
8. 校验通过后保存志愿主表和明细表。
9. 用户可切换 5 份方案进行比较。

### 10.4 院校 Excel 导入流程
1. 管理员下载导入模板。
2. 按模板整理院校和专业数据。
3. 上传 Excel 文件。
4. 后端先保存文件，再启动异步导入任务。
5. 任务读取 Excel，并预加载已有院校和专业数据。
6. 按批次执行新增或更新操作。
7. 将导入进度写入上下文。
8. 前端轮询导入进度接口显示结果。

### 10.5 统计看板流程
1. 管理员进入首页。
2. 前端调用 `/entrance/statistics/overview` 和 `/entrance/statistics/chart`。
3. 后端根据当前角色决定统计范围。
4. 返回概览卡片数据与图表数据。
5. 前端使用 ECharts 进行可视化展示。

## 11. 系统特色与创新点

如果用于本科答辩，下面这些点很适合作为“设计亮点”：

### 11.1 多角色视图分离
系统管理员、学校管理员、普通考生三类角色使用同一套系统，但首页、菜单和数据范围不同，体现了较好的权限与业务分层设计。

### 11.2 志愿填报规则校验
系统并非只保存用户选择，而是在保存前自动核验“学生选科是否满足专业要求”，提高了系统的智能辅助能力。

### 11.3 多方案志愿单设计
支持 5 份志愿单并行保存，贴合高考生会准备多套方案进行对比的实际需求。

### 11.4 异步导入与进度追踪
大规模院校专业数据导入采用异步执行和进度追踪，解决了传统同步导入易超时、体验差的问题。

### 11.5 可视化统计分析
系统使用看板图表展示热门专业、用户注册趋势和志愿填报趋势，提升了数据洞察能力。

## 12. 系统不足与可优化方向

答辩时老师通常会问“你这个系统还有哪些不足”，建议从下面几个角度回答：

### 12.1 推荐算法仍然偏规则化
当前系统主要依据历史分数和选科要求做辅助判断，尚未引入更高级的推荐算法，例如基于位次、概率模型或协同推荐的智能推荐。

### 12.2 数据来源依赖人工维护
院校、专业、分数线等数据目前主要通过 Excel 或后台维护方式导入，后续可考虑接入自动采集或标准数据接口。

### 12.3 志愿风险评估还可以更深入
目前系统更多是“可填/不可填”的规则校验，未来可以进一步计算“冲、稳、保”分层建议与录取概率估计。

### 12.4 移动端适配还可加强
虽然当前前端具备一定响应式能力，但若面向大规模考生使用，后续可进一步优化移动端体验或开发小程序版本。

## 13. 部署与运行说明

### 13.1 后端运行
1. 安装 JDK 1.8。
2. 安装 MySQL，并创建数据库。
3. 导入 `college_entrance.sql` 及相关补充 SQL。
4. 修改 `application-dev.yml` 中的数据库连接配置。
5. 进入后端工程执行 Maven 构建。
6. 启动 `WebApplication`。

### 13.2 前端运行
1. 安装 Node.js。
2. 进入 `前端代码/example-ui`。
3. 执行 `npm install`。
4. 执行 `npm run dev`。
5. 通过浏览器访问前端地址。

### 13.3 接口联调
前端通过 `VUE_APP_BASE_API` 对接后端接口，后端默认端口为 `8082`，部署时需保证跨域和接口地址配置正确。

## 15. 答辩问答准备

### 15.1 如果老师问“你的系统核心难点是什么”
可以回答：

“我认为系统的核心难点主要有三个。第一是多角色权限控制，需要保证系统管理员、学校管理员和普通考生看到的菜单和数据范围不同。第二是志愿填报业务规则处理，尤其是学生选科与专业选科要求之间的匹配校验。第三是院校专业数据量较大，因此在 Excel 导入时我采用了异步导入和进度反馈机制，避免页面长时间阻塞。” 

### 15.2 如果老师问“你在项目里做了哪些关键设计”
可以回答：

“我主要做了前后端分离架构设计、基于 JWT 的登录鉴权、动态路由与权限菜单、学生档案与志愿方案模型设计、志愿填报选科校验逻辑、院校专业 Excel 异步导入、以及管理员统计看板等关键模块设计。” 

### 15.3 如果老师问“为什么选 Spring Boot + Vue”
可以回答：

“Spring Boot 适合快速构建稳定的 REST 接口，生态成熟，便于整合安全框架和数据库访问层；Vue 上手快、组件化能力强，适合实现后台管理和门户混合场景。两者配合可以很好地完成前后端分离开发，提高开发效率和维护性。” 

### 15.4 如果老师问“系统还有哪些改进空间”
可以回答：

“后续我希望从三个方向继续优化：第一，引入更智能的志愿推荐算法；第二，完善移动端体验；第三，对接更权威、更实时的数据源，提升推荐准确性和数据时效性。”
